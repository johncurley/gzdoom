# GPT audit findings: native Metal compute postprocess

Audited working tree scope from `GPT_AUDIT_CONTRACT.md`: AO first, bloom second, compute glue only where it affects those paths. This is a read-and-reason audit; I did not run the game on Metal hardware.

Note on independence: the conversation already included `AGENTS.md` content before this audit began, so I cannot honestly claim a blind read. I still derived the findings below from the code paths and mark them against `AGENTS.md` at the end.

## Findings

### 1. Compute bloom ignores camera exposure during extract

- **Files and lines:** `src/common/rendering/metal/shaders/native/mt_bloom.metal:33-46`, `src/common/rendering/metal/renderer/mt_bloom.cpp:346-383`, `src/common/rendering/metal/renderer/mt_postprocess.cpp:462-478`, reference path `wadsrc/static/shaders/pp/bloomextract.fp:4-11` and `src/common/rendering/hwrenderer/postprocessing/hw_postprocess.cpp:75-102`
- **Category:** visual-quality (parity)
- **Severity:** medium
- **Confidence:** high
- **Failure scenario:** With `mt_compute_bloom 1`, `gl_bloom 1`, default live exposure, and a scene where `hw_postprocess.exposure.CameraTexture` is not `1.0`, the compute path extracts `max(color.rgb - 1.0 + 0.001, 0)` while the reference path extracts `max((color.rgb + 0.001) * exposureAdjustment - 1.0, 0)`. In dark scenes where exposure raises the image, pixels with raw color below `1.0` but exposure-adjusted color above `1.0` do not bloom in the compute path, so compute bloom is dimmer and less adaptive than the reference path. If exposure adjustment is below `1.0`, the direction can reverse for bright pixels: compute bloom can keep pixels that the reference threshold would suppress.
- **Falsification test:** Fixed-camera A/B in a scene where the exposure texture is visibly not `1.0`: compare `mt_compute_bloom 1` against `mt_compute_bloom 0` after `mt_metrics_reset`, with bloom enabled and the same `gl_bloom_amount`. A pure numerical shader test would sample a color such as `0.8` with `exposureAdjustment = 1.5`: reference extract yields about `0.2015`, compute extract yields `0`.
- **Fix direction:** Thread the exposure texture into `MtBloomModule::Execute` and bind it to `bloom_extract`, matching the reference operation by multiplying exposure before thresholding: `(color.rgb + 0.001) * exposureAdjustment - 1.0`. Do not fold exposure into a scalar threshold unless the intended behavior is only algebraic equivalence for the color term and not exact parity: the `+0.001` bias is also multiplied by exposure in the reference path, and the current reference samples an exposure texture, not a fixed cvar scalar.
- **AGENTS status:** already documented in `AGENTS.md:2189-2202`. This finding confirms that reading from the code.

### 2. The inline AO fallback source is missing `SSAOParams::noiseCellSize`

- **Files and lines:** fallback declaration in `src/common/rendering/metal/renderer/mt_ao.cpp:76-97`; native declaration in `src/common/rendering/metal/shaders/native/mt_ao.metal:40-62`; CPU declaration in `src/common/rendering/metal/renderer/mt_ao.h:42-62`; fallback use sites begin at `src/common/rendering/metal/renderer/mt_ao.cpp:184-201` and `src/common/rendering/metal/renderer/mt_ao.cpp:334-344`
- **Category:** maintainability (parity)
- **Severity:** medium
- **Confidence:** high
- **Failure scenario:** If `native_shaders.metallib` is missing or fails to load, `MtShaderManager::CreateComputePipeline(...)` compiles `SSAO_COMPUTE_SOURCE` from `mt_ao.cpp`. That fallback `SSAOParams` omits `float noiseCellSize`, but the fallback function bodies still reference `params.noiseCellSize` in `NoiseCellSize` and debug output. The likely result is AO fallback shader compilation failure, leaving the compute AO PSOs null and causing Metal to fall back to the PP AO path instead of exercising the intended inline fallback. The default shipped native path is not affected because `mt_ao.metal` and the CPU struct both include the field in the same order.
- **Falsification test:** Temporarily force native library loading to fail or remove/rename the bundled metallib, then launch with `mt_compute_ao 1` and check the Metal log for fallback shader compilation errors mentioning `noiseCellSize`. A cheaper static check is to extend `tools/check_shader_parity.py` to compare shared struct declarations; it should fail on current `SSAOParams`.
- **Fix direction:** Add `float noiseCellSize;` to `SSAO_COMPUTE_SOURCE` immediately after `fadeEndDistance`, matching `mt_ao.metal` and `mt_ao.h`. Also extend the parity script so it compares shared struct declarations or at least verifies field-name sets for `SSAOParams`, `AOBlurParams`, `AOFullresParams`, `BloomParams`, and `BloomCompositeParams`.
- **AGENTS status:** partially already documented as a general risk class: `AGENTS.md` says native/inline shader drift has happened and the parity script should pass. This specific struct-declaration drift is new relative to the notes I saw, and it is not caught by the current parity script.

### 3. Coverage mask render/sample coordinates do not obviously match scene coordinates outside a full-screen viewport

- **Files and lines:** mask allocation at `src/common/rendering/metal/renderer/mt_ao.cpp:1460-1468`, mask render pass at `src/common/rendering/metal/renderer/mt_ao.cpp:2079-2109`, AO sample use at `src/common/rendering/metal/shaders/native/mt_ao.metal:353-356`, `src/common/rendering/metal/shaders/native/mt_ao.metal:536-539`, and `src/common/rendering/metal/shaders/native/mt_ao.metal:760-763`; scene viewport scale/offset source at `src/common/rendering/v_video.h:201-209`
- **Category:** correctness
- **Severity:** low
- **Confidence:** medium
- **Failure scenario:** `mCoverageMask` is allocated at AO resolution, but `RenderCoverageMask` renders it using the full scene depth/stencil attachment and a raw fullscreen triangle without setting viewport/scissor or applying `SceneScale`/`SceneOffset`. The AO kernels sample scene color/depth/normal at `sampleSceneUV = offset + sampleUV * scale`, but sample the coverage mask at unscaled `sampleUV`. When `mSceneViewport != mScreenViewport` or when portal stencil coverage is not uniform, the mask can reject or admit samples for a different screen location than the depth/color sample. False rejection lowers accumulated occlusion and brightens; false admission allows cross-portal/depth-layer samples and can darken or halo, with the artifact anchored to viewport/stencil layout rather than scene geometry.
- **Falsification test:** Use a fixed camera with a non-full-screen scene viewport or a visible portal/stencil boundary. Compare `mt_compute_ao 1` with the coverage mask forced all-white, or temporarily bind no `coverageTex`/skip the `sampleCov < 0.5` branch, while keeping all AO cvars fixed. If the artifact remains identical, this is not the source. If a band or portal-edge AO changes without corresponding scene-geometry movement, the mask coordinate path is implicated.
- **Fix direction:** Make the mask coordinate space explicit. Either render `mCoverageMask` as a true downsample of the scene viewport/stencil domain that corresponds to AO local UVs, or sample it with the same scene-scaled UV as other scene inputs and ensure its render pass populates that same domain. Also consider setting viewport/scissor explicitly in `RenderCoverageMask` rather than relying on raw encoder defaults.
- **AGENTS status:** new relative to the visible notes. The notes mention the coverage mask as a portal guard but do not discuss this coordinate-space mismatch.

## Specific questions

### Q1: Bloom exposure divergence

Confirmed. The compute extract thresholds raw scene color, while the reference extract thresholds exposure-adjusted color from `hw_postprocess.exposure.CameraTexture`. The correct parity operation is exposure multiplication before thresholding:

```metal
float exposureAdjustment = exposureTexture.sample(...).x; // reference samples vec2(0.5)
float3 res = max((c.rgb + 0.001) * exposureAdjustment - 1.0, 0.0);
```

Folding exposure into a threshold is not the same operation for exact parity because the reference multiplies the small bias too, and because the source of exposure is a texture produced earlier in `Pass1`, not just the static exposure cvars.

### Q2: AO lower-viewport residual darkening

Mechanisms that can create a lower-viewport effect rather than scene-locked geometry:

- **Off-screen sample rejection itself:** after the recent change, off-screen samples `continue` but the final denominator remains `numDirections * numSteps` or `sampleCount`. The sign is brightening, not darkening, because rejected samples add no occlusion. If strafing shows a lower-edge bright or weak-AO band fixed to the viewport, this path is plausible. It does not explain a dark band by itself.
- **Border clamp during upsample/combine/blur:** low-res upsample clamps AO taps to the AO texture edge, and combine samples neighboring AO with clamp-to-edge. This can smear whatever value already exists at the AO border inward. Direction depends on the source edge value: if the edge AO is dark for another reason, this can make the darkening fixed to the lower viewport.
- **Coverage mask coordinate mismatch:** if the mask is in a different coordinate space than `sampleSceneUV`, false admissions can allow cross-stencil samples and over-occlude in regions fixed to the viewport/stencil layout. False rejections brighten. A strafe test where the dark patch stays in the same screen region while scene geometry moves implicates viewport-space mask/combine/border handling more than AO math.
- **World/screen mixed noise on grazing geometry:** lower-screen floor/wall grazing angles can show correlated noise because the lower viewport often contains nearby grazing surfaces. This tracks the world surface under strafe/turn rather than staying glued to the screen. If the blotches move with the floor/wall texture or geometry, the noise/cell-size/thickness path is implicated instead of viewport border handling.
- **Depth/thickness/fade heuristics:** these are geometry/depth dependent. A darkening that follows nearby floor/wall geometry during strafe points here; a darkening that remains at the same normalized screen Y while different geometry passes through does not.

The discriminating strafe test: keep the camera angle fixed and strafe sideways. If the darkening is fixed to the lower screen region, prioritize coverage-mask coordinates, AO border clamping/smear, and combine/upsample viewport mapping. If it tracks world geometry, prioritize noise decorrelation, grazing-angle sample distribution, thickness rejection, and distance fade.

`AGENTS.md:2073-2076` already records the residual as open and names the same strafe split at a high level; the coverage-mask coordinate hypothesis above is new relative to the visible notes.

## Looked at hard and did not file

- **AO CPU/GPU parameter layout for the native path:** `SSAOParams` in `mt_ao.h` and `mt_ao.metal` match in field order around the recently added `noiseCellSize`, `debugMode`, `pixelWorldScale`, and `screenNoiseMix`. The native path is not the inline fallback bug.
- **AO Y flip:** I did not find a supported Y-flip finding. The sample kernels keep `flipY = 0`; the render combine flips all scene inputs together in `ssao_combine_fs`, and I do not have a full round-trip showing a wrong fetched texel.
- **AO off-screen rejection sign:** rejected samples reduce occlusion contribution while the denominator stays fixed, so the direct sign is brightening near borders. I did not file it as a darkening cause.
- **Bloom Tier 2 gating:** I did not report the read-write BGRA path as broken. It is correctly gated away on the Intel HD 6000 profile described in the contract.
- **Objective-C/metal-cpp ownership:** I did not find an ownership leak worth reporting. `new*` results are generally retained and released; autoreleased factory calls were not treated as leaks.
