THE HEADLINE — every Metal postprocess pass was mirroring V, and the chain
only worked when the pass count happened to be even

- The shared fullscreen triangle (flatvertices.cpp:66-68) maps UV.y with NDC.y,
  which is correct only under OpenGL's bottom-left texture origin. Metal's is
  top-left, so every PP pass that sampled a texture and wrote it out flipped V.
- BlitSceneToPostprocess flipped once and the final Present flipped again, so
  an EVEN pass count came out upright. Any effect adding an ODD number of
  passes inverted the whole frame. Fixed 5a9b53e1b.
- MEASURED, one variable at a time:

      gl_fxaa 1       2 draws   even   upright     <- accidentally worked
      gl_lens 1       1 draw    odd    INVERTED
      gl_tonemap 1-5  1 draw    odd    INVERTED

- gl_tonemap 4 is a mathematical identity, sqrt(c*c) == c, and it inverted the
  frame too. That is what proved the defect was in the plumbing and not in any
  shader's maths, and it made the fix falsifiable: with orientation correct,
  mode 4 must be byte-identical to mode 0. It is —

      gl_tonemap 0   md5 326268d2e5070b81cf9f115d655011bb
      gl_tonemap 4   md5 326268d2e5070b81cf9f115d655011bb

Also fixed today, each verified

- PixelFormat::Rgba8 mapped to BGRA8Unorm (ad35e9a52). Vulkan uses
  R8G8B8A8_UNORM, GL uses GL_RGBA8. Transposed R and B in the palette tonemap
  LUT and in custom PP shader textures — the latter is a user-facing bug for
  modders. Invisible until now because the other Rgba8 textures in play are
  noise-like (dither), where a channel swap cannot be seen.

THE STANDING LIST

1. **AO computes but never reaches the screen.** gl_ssao 0 vs gl_ssao 3
   produce BYTE-IDENTICAL frames, yet AO is running and correct. Everything
   below is measured, not inferred:
     - PPCPU AO present, samples=120, at gl_ssao 3; absent at gl_ssao 0, so
       the cvar applies and the pass really is gated off.
     - gl_ssao_debug 1 shows a healthy occlusion buffer, aligned with the real
       geometry (dark in the actual concave corners).
     - gl_ssao_debug 7 (step(1e-5, ssao.y)) is white everywhere: the depth
       channel is populated.
     - gl_ssao_debug 3 (ssao.yyy/1000) measured min 43, median 75, max 106 —
       correct WORLD units for this compact interior. So the shader's
       `ssao.y > 2.0` gate PASSES, and depthMask ~= 0.38.
     - Computed alpha should therefore reach ~0.11 in corners. An 11% blend
       cannot produce byte-identical frames.

   BlendMode through PP pipeline creation (mt_postprocess.cpp:303-320), so
   this needs a fresh look rather than another capture.

**colormap is the one that matters and it is not a cvar at all.**
PPColormap::Render returns early only when `flash == 1.f` and fixedcm is not a
special colormap. A palette flash — taking damage, picking up an item — or a
special colormap makes it run ONE draw. Pre-5a9b53e1b that means the screen
flipped upside down every time the player got hit. It survived unnoticed
because all testing happens standing still at a pinned savegame where nothing
ever flashes. Every other item on this list required opting in via a cvar;
this one did not.

Still untested. `give invulnerability` FAILS in Ashes 2063 ("Unknown item") —

player.fixedcolormap directly (powerups.zs:221):

and can be screenshotted at leisure rather than racing a few-tic flash.

NEW: THIS VIEWPOINT CAN REPRODUCE BIT-EXACTLY — BUT ONLY ONE DIRECTION OF THE
RESULT IS TRUSTWORTHY

Two launches of an identical config produced byte-identical PNGs
(ssao3a == ssao3b, md5 af8e771f...), and so did the pre-fix AO pair
(092337f8...). So md5 CAN settle a question here, far more cheaply than the
blob statistics used up to now.

**The asymmetry is the whole point, and an earlier draft of this handoff got it
wrong by claiming a zero noise floor outright:**

  - BYTE-IDENTICAL is strong. It means no drift occurred AND the change under
    test did nothing. Both at once. tonemap 0 == 4 and the pre-fix AO pair are
    solid on this basis.
  - BYTE-DIFFERENT is AMBIGUOUS. It is equally consistent with a real effect
    and with exposure drift between launches, and it needs a same-config
    control pair before it means anything.

MEASURED counterexample, so this is not theoretical. gl_fxaa 0 vs gl_fxaa 1,
captured in two launches with gl_exposure_speed 1 set in both:

    mean signed delta +4.12   brighter 279948 px (39.3%)   darker 6650 (0.9%)

FXAA is edge antialiasing; its difference must be thin, edge-local and roughly
symmetric. A broad one-directional BRIGHTENING over 39% of the frame,
concentrated on the lantern and crate, is exposure adaptation — the exact shape
tools/localize.py's docstring warns about. The FXAA question is still open
because of it.

Determinism holds for the same elapsed FRAME COUNT, not the same wall clock.
Exposure adapts over frames, so a screenshot taken sooner or later after load
converges differently even with gl_exposure_speed 1. ssao3a/ssao3b happened to
be captured at comparable elapsed times; the fxaa pair was not.

Anything with animation, RNG, or a moving viewpoint will not reproduce at all.

CAPTURE PROTOCOL — unchanged, and it was violated again today at a cost

1. Pin the viewpoint with capspot.zds (MAP51 lantern).
2. ONE LAUNCH PER CONFIGURATION, cvars on the command line. The operator types
   only `screenshot`.
3. Never chain console commands with `;`.
4. The console pauses the game and GetScreenshotBuffer only re-presents, so a
   shot taken with the console open reflects the last frame rendered with it
   CLOSED. This applies to the ENGINE's screenshot command. macOS Cmd+Shift+4
   sidesteps it entirely by capturing the live window.
5. -exec runs before `Init complete.` and +screenshot never fires.

What went wrong today: cvars were typed into a running console instead of one
launch per config. `gl_lens 1` was set and never set back, so it silently
applied to four later captures INCLUDING an mt_bloom_dump, and the whole batch
had to be redone. Setting a cvar on the command line also means the frame
before you open the console already has the right config, which is what makes
rule 4 safe.

Note +mt_caps on the command line prints viewport numbers from before the first
frame (it reported `Scene viewport: 0,386 0x773`). The format line is valid;
the viewport lines are not. Type it in the console if you need those.

THE METHOD LESSONS — the expensive ones

- **A test whose two outcomes look the same is not a test.** gl_fxaa 1 was
  designed to prove the pass-parity theory and came back upright, apparently
  falsifying it. FXAA is TWO draws, so an even count was the theory's own
  prediction. Count the draws before predicting the parity.
- **Prefer an effect whose application is self-evident.** gl_lens was the test
  that worked, partly because barrel distortion is unmistakable: a null result
  could not masquerade as a pass. FXAA's subtlety made its null undetectable.
- **A mathematical identity is the strongest available probe.** gl_tonemap 4
  removed the shader maths as a variable entirely.
- **Byte-identical captures are ambiguous, ALWAYS.** They mean "perfect
  identity" and "the pass never ran" equally well. What distinguished them for
  tonemap 4 was the PRE-fix observation that mode 4 visibly broke the frame.
  What distinguished them for AO was the PPCPU AO metric label.
- **Measure the magnitude, do not eyeball the image.** gl_ssao_debug 3 looked
  "near-black, so the depth must be normalised" — the obvious reading, and
  wrong. Sampling the actual pixels gave 43-106 world units and overturned the
  diagnosis. The launch was worth it precisely because it could overturn it.
