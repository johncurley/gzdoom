THE HEADLINE — the compute-vs-reference bloom difference is SOLVED, and the
compute path was right all along

- `MtShaderManager::CompileShader` keyed its in-memory `mShaderCache` on the
  shader NAME alone. PPShaders that share a fragment filename and differ only
  in `Defines` collided, and the second one requested silently received the
  first one's compiled module. `shaders/pp/blur.fp` is both BlurHorizontal and
  BlurVertical, and RenderBloom runs horizontal first — so **every "vertical"
  blur in Metal's PP bloom was a second horizontal blur.** Fixed b017e7c92.
- After the fix the two paths agree at every pyramid level: L0 109x90 vs
  112x90, L2 and L3 extents identical, peak within 1.9%, energy 2.4%, pixel
  count 3.0%.
- Found by measurement, not reading. The row that did it:

      after horizontal   78x41   1.90:1   px=888
      after vertical     78x41   1.90:1   px=927   <-- bbox UNCHANGED

  A blur that does not move the bounding box is not blurring along that axis.
  Four source-reading passes had already cleared this code.

Also fixed today, each verified

- Composite V-flip (3cb088b89), CONFIRMED ON SCREEN at two viewpoints —

- `PixelFormat::Rgba16f` mapped to BGRA8Unorm on Metal (3531ea502). Vulkan
  uses R16G16B16A16_SFLOAT, GL uses GL_RGBA16F. The only shared-code consumer
  is the bloom pyramid, so Metal's reference bloom ran entirely in 8-bit LDR,

  would have disagreed exactly on a cold load.

CAPTURE PROTOCOL — use this, three rounds were lost before it existed

1. Pin the viewpoint with a savegame (`capspot.zds` exists, MAP51 lantern).
   Absolute pixel numbers are comparable only within a viewpoint; across
   rounds only RATIOS survive.
2. One launch per configuration with cvars on the command line, so the setting
   is live from the first rendered frame. The operator types only
   `screenshot`.
3. Never chain console commands with `;` — it silently dropped a cvar and
   produced a phantom "compute bloom does nothing" result.
4. The console pauses the game and `GetScreenshotBuffer` only re-presents, so
   a shot taken with the console open reflects the last frame rendered with it
   CLOSED. This produced seven byte-identical shots across four toggles.
5. `-exec` runs before `Init complete.` and `+screenshot` never fires. Neither
   can drive a capture sequence.

THE METHOD LESSONS — the expensive ones

- **When an elimination argument concludes the divergence must be somewhere
  you have already cleared, suspect the assumption, not the location.** I
  argued "a separable Gaussian cannot elongate a blob, therefore the
  reference's extract must already be elongated, therefore the bug is in the
  extract." The extracts then measured identical. The deduction was valid; it
  assumed the code did what it said.
- **Prefer a test comparing two live measurements over one comparing a
  measurement to a number derived from it.** The V-flip was originally
  "confirmed" by arithmetic whose reflection axis was fitted from the midpoint
  of the two measurements it explained. The real confirmation was that the two
  paths landed in the same place.
- **Predict a relationship between things you will measure together, not an
  absolute from an old session.** A predicted centroid of 424.6 was
  unreachable because it came from a different viewport.
- **Debug code must not materialize or perturb what it inspects.** Two
  self-inflicted bugs: a probe called GetPPTexture, which CREATES the texture,
  asserting on a 0x0 descriptor; and a readiness check did a blocking GPU
  readback every frame, slowing the frame rate until its own countdown never
  elapsed.
- **"Clear the cache" is not a general answer to "my shader change had no
  effect."** The on-disk cache was always keyed correctly; only the in-memory
  map was wrong, so no amount of clearing could have surfaced it.
